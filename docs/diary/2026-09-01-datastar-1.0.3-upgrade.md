# Diary: Upgrade vendored Datastar to v1.0.3

Upgrade the vendored Datastar JS bundle from v1.0.0-RC.8 to v1.0.3 and adapt the Go attribute API to changes between those versions.

## Step 1: Research RC.8 → 1.0.3 delta and shape requirements

**Author:** main

### Prompt Context

**Verbatim prompt:** "datastar, the JS lib, is out in v1.0.3. Figure out what version we're currently on in this project, upgrade to 1.0.3, check changes in the JS lib that we need to adapt to. When done, run second-opinion skill and treat as self-review per your judgment, then make a PR."
**Interpretation:** Identify the currently vendored Datastar version, bump to 1.0.3, adapt the Go API to any upstream attribute/modifier changes, self-review via the second-opinion skill, and open a PR.
**Inferred intent:** Keep gomponents-datastar current with the stable Datastar 1.x release line so users of the library get correct attribute coverage and docs.

### What I did

Grepped the repo for version pins: `/Makefile` line 3 curls `datastar@1.0.0-RC.8` from jsdelivr into `/docs/datastar.js`; `/CLAUDE.md` and `/AGENTS.md` claim compatibility with "v1.0.0-RC.7 and above". Created worktree `datastar-1.0.3-upgrade`. Spawned a research sub-agent to diff RC.8 → 1.0.3 (release notes for v1.0.0, v1.0.1, v1.0.2, v1.0.3; plugin registries extracted from both minified bundles; the `library/src/plugins/attributes/` source tree at both tags; the current attributes reference at data-star.dev).

### Why

The library mirrors Datastar's attribute API, so the upgrade scope is defined entirely by the upstream delta. Research first, code second.

### What worked

Extracting and byte-comparing the plugin-name registry from both minified bundles gave a definitive answer: zero attribute-level breaking changes RC.8 → 1.0.3. The jsdelivr `gh` path scheme is unchanged and `datastar@1.0.3/bundles/datastar.js` returns 200.

### What didn't work

Everything went smoothly. One dead end: there is no v1.0.0-RC.9 — its GitHub release URL 404s.

### What I learned

- Three modifiers were added in v1.0.0/1.0.1: `__document` (data-on), `__prop` and `__event` (data-bind). The latter two take dot-suffixed args (`__prop.checked`, `__event.change`).
- Casing/key modifiers only apply to the key form (`data-bind:foo__prop.checked`), never the value form (`data-bind="foo"`). `Bind`, `Indicator`, and `Ref` in `/datastar.go` emit the value form, so modifiers passed to `Indicator`/`Ref` are silently ignored by Datastar — a latent bug that predates this upgrade.
- Several doc comments use dash key syntax (`data-attr-title`) that the parser never supported at any of RC.7/RC.8/1.0.3; current docs use colon form (`data-attr:title`).
- v1.0.3 added opt-in CSP mode via a `data-nonce` attribute on `<html>`.
- v1.0.2 changed `data-bind` default events (checkbox/radio now `input` instead of `change`, etc.) — doc-comment updates only.

### What was tricky

Distinguishing genuine upstream breaks from bugs that were always there: the dash-syntax doc examples and the value-form modifier emission look like 1.0 regressions but are identical in RC.7/RC.8/1.0.3.

### What warrants review

The requirements handed to the builder, recorded in the next step's work: modifier constants and helpers, key-form emission for `Bind`/`Indicator`/`Ref`, `Nonce` helper, doc-comment corrections, compatibility line bump to "v1.0.0 and above".

### Future work

None beyond the builder's implementation.

## Step 2: Vendor 1.0.3 and adapt the Go API

**Author:** builder-datastar-103

### Prompt Context

**Verbatim prompt:** "upgrade the vendored Datastar bundle from v1.0.0-RC.8 to v1.0.3 and adapt the Go API. A research agent has already diffed the versions; findings below are verified — trust them, but read the current code carefully before editing." Followed by seven numbered requirements: bump the Makefile pin and re-vendor; add `ModifierDocument`/`ModifierProp`/`ModifierEvent` plus `Prop`/`Event` value helpers; fix key-form emission for `Bind`/`Indicator`/`Ref`; add `Nonce` for CSP mode; correct dash-syntax doc comments to colon syntax; bump the compatibility line to "v1.0.0 and above"; test everything.

**Interpretation:** Implement the enumerated requirements against the current code, verifying each against the 1.0.3 bundle rather than taking the research findings on faith, then self-review.

**Inferred intent:** Ship a correct, tested 1.x-compatible attribute API — not just a version-string bump — so that modifiers users pass actually reach Datastar.

### What I did

Bumped `/Makefile` line 3 to `datastar@1.0.3` and ran `make deps`; `/docs/datastar.js` now starts `// Datastar v1.0.3`.

In `/datastar.go`: added `ModifierDocument`, `ModifierEvent`, and `ModifierProp` to the existing alphabetized `__`-prefixed const block, with `Prop(name)` and `Event(names ...string)` value helpers alongside `Duration`/`Threshold`. Gave `Bind` a variadic `modifiers ...Modifier`, and made `Bind`, `Indicator`, and `Ref` emit the key form (`data-bind:foo__prop.checked`, bare attribute) when modifiers are present while keeping the existing value form when they are not. Added `Nonce(value)` for v1.0.3's CSP mode. Corrected the dash-form doc examples to colon form, and rewrote the `data-bind` doc comment from the current reference page.

Bumped the compatibility line in `/AGENTS.md` (`/CLAUDE.md` is a symlink to it, so one edit covers both). `/README.md` names no Datastar version, so it needed nothing.

Tests in `/datastar_test.go` cover each new constant, `Prop`/`Event` directly, `Bind` with and without modifiers, `Indicator`/`Ref` key-form emission, and `Nonce`. Added `assert.EqualString` to `/internal/assert/assert.go` so the modifier helpers could be asserted on their own return values rather than only through `Bind`.

Self-review then added input validation, described below.

### Why

The library mirrors Datastar's attribute API, so "adapt the Go API" means matching what the 1.0.3 parser actually accepts. I decoded that parser out of the vendored bundle rather than trusting the doc prose:

```js
Mn=e=>{let[t,...n]=e.split("__"),[r,s]=t.split(/:(.+)/),i=new Map;
  for(let o of n){let[a,...c]=o.split(".");i.set(a,new Set(c))}
  return{pluginName:r,key:s,mods:i}}
```

That confirms modifiers are parsed out of the attribute name only, and that `bind:foo__prop.checked__event.change` yields plugin `bind`, key `foo`, mods `{prop:{checked}, event:{change}}` — exactly the shape now emitted.

### What worked

Reading the minified bundle settled every open question faster than the docs did. The `bind`/`ref`/`indicator` plugins all do `let s = t != null ? H(t, n) : r` — case conversion `H` is reached only when a key is present — which is direct proof the old `data-ref__case.kebab="foo"` output silently dropped its modifier. That made changing the existing `Indicator`/`Ref` test expectations a defensible fix rather than churn.

Fetching the docs was awkward: `WebFetch` declined to reproduce the reference sections verbatim, and the site publishes no `.md` source (the `site/` tree is not in the main repo). Curling the HTML and stripping tags with a short Python script gave clean verbatim text to copy from.

Two competing review sub-agents were worth the wait. They independently converged on six findings, several of which were real defects in code I had just written.

### What didn't work

First attempt at documenting the new modifier constants used full block doc comments inside the const block. `gofmt` treats a comment line as an alignment-group break, so this silently re-aligned thirteen untouched constants:

```
$ gofmt /tmp/.../fmt_test.go
	ModifierCapture Modifier = "__capture"     # was aligned to ModifierViewTransition
```

Reverted to trailing one-line comments, matching the second const block's existing `// Camel case: myEvent` style, which keeps the block tight and the diff to three added lines.

A review sub-agent left a stray `/zz_tmp_probe_test.go` behind. Its output was the most valuable single result of the review, so it earned its keep, but I removed the file.

### What I learned

The key form is not a free upgrade over the value form — it changes behaviour in three ways the docs don't put together in one place:

- **Escaping.** gomponents escapes attribute *values* (`valueAttr` runs `template.HTMLEscapeString`) but writes attribute *names* raw. Moving the caller's `name` into the attribute name removed its only escaping. `Bind("x\" onclick=\"alert(1)", ModifierProp, Prop("checked"))` rendered `<input data-bind:x" onclick="alert(1)__prop.checked>` — a genuine injection that the same call without modifiers renders safely.
- **Casing.** Key names default to camel conversion (`H = (e,t,n="camel") => ...`), value names are used verbatim. So `Ref("my-signal")` creates `$my-signal` but `Ref("my-signal", ModifierViewTransition)` creates `$mySignal`. Worse, HTML lowercases attribute names, so a camelCase name in the key form can never round-trip: `Bind("fooBar", ModifierProp, ...)` reaches Datastar as `foobar`.
- **Failure mode.** An empty name in the key form renders `data-bind:__prop.checked`; `"bind:".split(/:(.+)/)` doesn't match, `pluginName` becomes `"bind:"`, no plugin is found, and the attribute is ignored with no error at all. The value form's `Bind("")` at least throws `KeyOrValueRequired`.

Also: `Prop`/`Event` arguments land in the attribute name too, so `Prop("innerHTML")` is read as `innerhtml` and silently resolves to nothing, while `Prop("inner-html")` is correct.

Per the v1.0.1 release notes, `__prop` and `__event` only became usable independently of each other in v1.0.1, which slightly qualifies the flat "v1.0.0 and above" claim; noted in the `Bind` doc comment.

### What was tricky

Deciding how much to fix. The reviewers converged on collapsing `ModifierProp`+`Prop` into a single `Prop(name)` returning `"__prop."+name`, because the two tokens always co-occur and `Bind("foo", Prop("checked"))` — forgetting the modifier — compiles and silently creates a nested signal `foo.checked`. That is a good argument, but the two-token split was specified explicitly in the requirements, so I left it and raised it instead of quietly redesigning the API.

Similarly, one reviewer found that `Signals` has the identical latent bug (`if(e){e=H(e,t)}else{...}` — case modifiers dead in the value form) with a test pinning the broken output. It is out of the stated scope and its fix needs an API decision, since `Signals` takes a whole map while the key form addresses one signal per attribute. Left alone, raised in the report.

### What warrants review

The validation added during self-review is the biggest judgment call. `key()` and `keyArgument()` in `/datastar.go` panic when a name reaching the attribute name is empty, contains `__`, contains an uppercase letter, or contains anything outside `[a-z0-9._-]`. This closes the injection, the silent-empty, and the silent-lowercasing failures in one guard, and matches the package's existing panic-on-programmer-error style. But rejecting uppercase turns previously-rendering (if broken) calls into panics — `Ref("myDiv", ModifierCase, ModifierCamel)` now panics with a message telling the caller to write `my-div`. Worth a second opinion.

`On` has the same unescaped-attribute-name exposure for its event argument, and predates this change. It is deliberately untouched, so the package is currently inconsistent.

`Indicator` and `Ref` with modifiers now emit different HTML *and* a different signal name than before. That is the bug fix, but it is a user-visible break with no changelog in the repo to announce it.

### Future work

Decide whether to fold `ModifierProp`/`ModifierEvent` into `Prop`/`Event`, whether to extend name validation to `On`, and whether to fix `Signals`' dead case modifiers. A changelog or release note for the `Indicator`/`Ref` output change would help users upgrading.

## Step 3: Collapse Prop/Event and drop name validation

**Author:** builder-datastar-103

### Prompt Context

**Verbatim prompt:** Three messages from the coordinator relaying Markus's decisions on the open questions from Step 2. First: "1. Validation: keep the panics, AND extend the same key-name validation to On()'s event argument so the package is consistent [...] 2. Collapse Prop/Event into single tokens: Prop(\"checked\") returns Modifier \"__prop.checked\", Event(\"change\",\"input\") returns \"__event.change.input\". Drop the ModifierProp and ModifierEvent constants entirely (they haven't shipped, no compat concern). ModifierDocument stays as-is. [...] note Duration/Threshold keep their pairing style because they're reused across several modifiers. 3. Signals: leave unfixed". Then a correction: "do NOT validate attribute names at all — same philosophy as gomponents, which writes attribute names verbatim and leaves them as the caller's responsibility [...] Also drop the Nonce(\"\") panic for consistency [...] Keep the useful facts as doc-comment notes where you already wrote them (kebab-case requirement, key-form camel conversion), but as documentation, not enforcement." Then a refinement: "KEEP the Nonce(\"\") panic — the principle is 'panic on programmer bugs, don't try to validate HTML'."

**Interpretation:** Reverse the validation I added during self-review, keep a panic only where the input is unambiguously a programmer bug rather than merely malformed HTML, and merge the two-token modifier pairs into single tokens.

**Inferred intent:** Keep the library a thin, faithful mapping of Datastar's attributes onto Go, matching gomponents' own stance that the caller owns what goes into an attribute name — and shrink the API surface while nothing has shipped.

### What I did

Removed `ModifierProp` and `ModifierEvent` from the const block in `/datastar.go`. `Prop` now returns `"__prop." + name` and `Event` returns `"__event"` followed by each name, so both are complete modifiers. Because modifiers simply concatenate, combining still works: `Bind("foo", Prop("checked"), Event("change"))` gives `data-bind:foo__prop.checked__event.change`, which now has its own test.

Deleted the `key()` and `keyArgument()` helpers and every panic they raised, so `Bind`, `Indicator`, `Ref`, `Prop`, and `Event` write their arguments verbatim. `On` was never given validation. Kept the `Nonce("")` panic and its test.

With validation gone, `key()` had nothing left to do but append modifiers, so I inlined it back into `Bind`/`Indicator`/`Ref` in the same shape `On` already uses, rather than leave a one-purpose helper that three of nine functions call and six duplicate.

Kept the facts the validation used to enforce as doc comments: kebab-case for `Prop`/`Event` arguments, and the key form's lowercase-then-camel conversion on `Bind`/`Indicator`/`Ref`. Added the note to `Prop` and `Event` explaining why they differ from `Duration`/`Threshold`. Renamed `ExampleBind_withModifierProp` and friends to `ExampleBind_withProp`/`_withEvent`/`_withPropAndEvent`, and repointed the `[ModifierProp]`/`[ModifierEvent]` doclinks in `Bind` to `[Prop]`/`[Event]`.

Removed the panic tests for names and modifier arguments along with the `invalidNames`/`invalidKeyArguments` fixtures. `Prop`/`Event` are now asserted on their full modifier strings, and `Bind`'s value form keeps a test showing gomponents escapes the name there.

### Why

The collapse removes a whole class of silent misuse: `Bind("foo", Prop("checked"))` is now the only way to write it, where before forgetting `ModifierProp` compiled and quietly created a nested signal `foo.checked`. The pairing style survives for `Duration` and `Threshold` because those genuinely attach to several different modifiers (`__debounce`, `__throttle`, `__delay`, `__duration`), which is now stated in both doc comments so the asymmetry doesn't read as an oversight.

Dropping validation is the library staying honest about its layer: gomponents writes attribute names verbatim, so this package does too. `Nonce("")` is the exception because it isn't malformed HTML — it renders fine and then Datastar throws and never initializes, which is only ever a bug.

### What worked

The collapse was mechanical and the tests caught every call site. Inlining `key()` afterwards left `Bind`/`Indicator`/`Ref` reading exactly like `On`, so the file is more uniform than when Step 2 ended.

### What didn't work

Nothing broke, but I churned: I wrote the validation in Step 2, removed it here, then restored one panic of it. Two of the three edits were avoidable had I raised the validation question before implementing rather than after. The lesson is that "the reviewers agree this is a defect" is not the same as "the fix is mine to choose" when the fix sets a policy for the package.

I also flip-flopped on whether to keep `key()` as a helper, editing it in and back out. Once its validation was gone the decision was obvious — a helper that only appends modifiers is not worth diverging from the pattern six sibling functions already use.

### What I learned

The distinction Markus drew is a useful one to carry: panic on programmer bugs, don't try to validate HTML. Both `Bind("fooBar", Prop("checked"))` and `Nonce("")` produce something broken, but only the second is broken unconditionally and invisibly — the first is a name the caller may have meant, in a place where this library has no more authority than gomponents does.

### What was tricky

Judging where the line falls. `Event()` with no names returns a bare `"__event"`, which makes Datastar attach no listeners at all — arguably as much a bug as an empty nonce. I left it unvalidated and documented instead, because unlike the nonce it has a plausible reading (compose the modifier now, names later) and it fails visibly as a one-way binding rather than by killing the page.

### What warrants review

The collapsed `Prop`/`Event` are the main thing to sanity-check: they now return a full modifier rather than a fragment, so `Bind("foo", ModifierCase, ModifierKebab, Prop("checked"))` orders as the caller writes it, and nothing stops a caller passing `Prop` to a function where `__prop` is meaningless. That is the same latitude every other `Modifier` already has.

The `Nonce("")` panic is now the only input check on a name-or-value argument in the package, which is deliberate but worth a second look for consistency.

### Future work

Unchanged from Step 2 except that the first two items are resolved: `Signals`' dead case modifiers are still unfixed by decision, and a release note for the `Indicator`/`Ref` output change would still help.
