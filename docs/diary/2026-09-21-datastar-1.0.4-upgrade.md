# Diary: Upgrade vendored Datastar to v1.0.4

Bump the vendored Datastar JS bundle from v1.0.3 to v1.0.4 and adapt the Go attribute API to any changes between those versions.

## Step 1: Research 1.0.3 → 1.0.4 delta and shape requirements

**Author:** main

### Prompt Context

**Verbatim prompt:** "Datastar 1.0.4 is out. Check the changes since 1.0.3 and update our project accordingly. See https://github.com/starfederation/datastar/releases/tag/v1.0.4"
**Interpretation:** Read the v1.0.4 release notes, determine which changes touch the attribute API this library mirrors, bump the vendored bundle, and adapt the Go code where needed.
**Inferred intent:** Keep gomponents-datastar current with the Datastar 1.x line so the vendored demo bundle and the Go API stay in step.

### What I did

Read the prior upgrade diary at `/docs/diary/2026-09-01-datastar-1.0.3-upgrade.md` and `/docs/decisions.md` for the established approach. Fetched the v1.0.4 release notes. Confirmed `/Makefile` line 3 pins `datastar@1.0.3` and `/docs/datastar.js` starts `// Datastar v1.0.3`. Downloaded the 1.0.4 bundle from jsdelivr into the scratchpad (HTTP 200, 33553 bytes) and diffed the sorted set of `name:"..."` plugin-registry entries between the two minified bundles.

### Why

The library mirrors Datastar's attribute API, so the upgrade scope is defined by the upstream delta at the attribute and modifier level. The plugin-registry diff is the cheapest definitive check for that.

### What worked

The plugin-registry diff came back identical between 1.0.3 and 1.0.4. The release notes match: the only additions are the `@query()` action (a JS expression action, which this library does not wrap — it has no `@get`/`@post` helpers either) and aliased nonce attributes in CSP mode (an alias-build feature; this library emits the default `data-` prefix only). Everything else is an internal fix: action rewriting inside string literals, request-cancellation races (#1205), object-signal key deletion reactivity (#1145), array-truncation patches, `data-json-signals` nested ordering, `data-animate`/`@fit()` clamping, error-code extraction, and Rocket becoming a free bundle.

### What didn't work

Nothing failed in research.

### What I learned

The 1.0.4 bundle reads the nonce attribute name from a variable rather than the literal `"data-nonce"`, which is the aliased-nonce change. It only matters for custom-alias builds, which this library does not target.

### What was tricky

Nothing. The scope is smaller than the 1.0.3 upgrade: no new attributes, no new modifiers, no changed defaults.

### What warrants review

The requirements handed to the builder: bump the Makefile pin, re-vendor the bundle, run the tests, and confirm the demo still initializes against the new bundle. No Go API changes are expected; if the builder finds any, that contradicts this research and should be flagged.

### Future work

None beyond the builder's implementation.

## Step 2: Bump the bundle, verify, sanity-check the demo

**Author:** builder-datastar-104

### Prompt Context

**Verbatim prompt:** "upgrade the vendored Datastar JS bundle from v1.0.3 to v1.0.4" with requirements: change the `deps` target's URL in `/Makefile`, run `make deps` and confirm `/docs/datastar.js` starts with `// Datastar v1.0.4`, run `make test` and `make lint`, sanity-check the demo in a browser (increment counter, toggle Bind Modifiers checkbox, check console for errors), leave `CLAUDE.md` as is, and add this diary step.
**Interpretation:** Mechanical re-vendor of the JS bundle plus verification that nothing broke, per the research in Step 1 which found no Go API changes needed.
**Inferred intent:** Ship the version bump with confidence, and flag rather than improvise if anything contradicts the research.

### What I did

Changed `/Makefile` line 3 from `datastar@1.0.3` to `datastar@1.0.4`, ran `make deps`, and confirmed `/docs/datastar.js` now starts with `// Datastar v1.0.4` (33553 bytes). Ran `make test` (`go test -coverprofile cover.out -shuffle on ./...`) — passed, 96.7% coverage, no changes needed. Ran `make lint` (`golangci-lint run`, which is installed) — `0 issues.` Served `/docs` with `python3 -m http.server 8123 --bind 0.0.0.0` and drove it with the playwright-cli skill: loaded `http://localhost:8123/`, clicked the counter's Increment button (went 0 → 1), and clicked the "I accept" checkbox under Bind Modifiers (`data-bind:accepted__prop.checked`), which toggled to checked and the page's "Accepted:" text flipped to `true`. The only console error across the whole session was the expected `favicon.ico` 404 from the static file server. Closed the browser, killed the http.server process, and removed the `.playwright-cli/` snapshot directory it left behind.

### Why

This is a pure re-vendor: Step 1's research already established there's no Go API surface to touch, so the job was to make the change, prove the bundle updated, and prove nothing regressed — in the Go test suite and in a live page exercising signals, data-bind, and two-way DOM sync against the new bundle.

### What worked

Everything matched the research exactly: no Go changes were needed, `make test` and `make lint` passed on the first try with zero modifications, and the demo behaved identically to what's expected on 1.0.3 — counter increments, checkbox binding, and the JSON signal dumps in the page all updated correctly with no new console errors.

### What didn't work

Nothing. No test failures, no lint issues, no unexpected console errors, no demo misbehavior.

### What I learned

Nothing new beyond Step 1's findings — this step was confirmation, not discovery.

### What was tricky

A minor self-inflicted snag: my first attempt at starting the demo server launched three `http.server` instances on different ports in a loop (meant to find "a free port" but ended up starting several). I killed the two extras and kept just the one on 8123 before proceeding.

### What warrants review

`git diff --stat` shows only `/Makefile` (1 line) and `/docs/datastar.js` (the vendored bundle) changed, plus the new diary file — no `datastar.go` or `datastar_test.go` changes, consistent with the research. Changes are left uncommitted per instructions.

### Future work

None. The upgrade is complete and verified; ready for the lead to review and commit.
